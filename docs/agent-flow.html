How the ASO Audit Agent works

A conversational agent that takes an App Store URL or numeric ID, confirms the listing with the user, then runs a multi-step Mastra workflow that gathers public evidence, scores eight ASO factors in parallel, and produces a grounded audit report with an action plan.

02 The two agents

Both share one model (asoAuditModel, default openrouter/openai/gpt-5-mini). They have deliberately different jobs and trust boundaries.

conversation-agent.ts

conversationAgent

The front door. Holds the chat, owns memory (last 30 messages + auto-title), and decides when to invoke the audit workflow.

  • Has memory (LibSQL) with generateTitle
  • Registers listingAuditWorkflow as a callable workflow
  • autoResumeSuspendedTools: true by default
  • Runs activeWorkflowSuspensionOnlyProcessor on input
report-agent.ts

reportAgent

The scoring brain. Stateless — no memory, no tools, no workflows. Invoked only from inside workflow steps via structuredOutput.

  • Treats listing/review/page text as untrusted evidence
  • Called 4× per audit (text, visual, market, action plan)
  • Each call: maxSteps:1, toolChoice:'none'
  • Every call has a deterministic fallback if the model fails

03 The audit workflow

Defined in workflows/listing-audit/workflow.ts. Linear except for a three-way parallel scoring fan-out, then a deterministic merge.

1
fetchMetadata app-lookup

Parses the URL/ID and calls iTunes lookup. Returns ~30 metadata fields (lookupAppMetadata).

2
userConfirmation suspends

Calls suspend() with “Is this the app you meant?” and the listing card payload. The run pauses here until the user confirms/rejects. Reject → bail() with a rejection narrative.

3
collectListingPageEvidence

Firecrawl scrape of the public listing page → subtitle, promo text, in-app events, screenshot URLs. Merges Apple-lookup screenshots in as backup.

4
collectMarketSignals

Parallel iTunes calls (Promise.allSettled): recent reviews RSS + related-app search. Failures degrade to notes, never throw.

5
Parallel scoring fan-out .parallel()

Three independent reportAgent calls run at once, each scoring its own slice of the 8 factors.

scoreListingTexttitle · subtitle · description · conversion
scoreVisualAssetsscreenshots · icon (image input)
scoreMarketSignalsratings/reviews · competitive pos.
6
assembleScoreCard deterministic

Merges the 3 branches, asserts all 8 factors present, applies fixed weights, computes the weighted overallScore, and sets confidence (high vs limited based on evidence completeness).

7
generateActionPlan

Fourth reportAgent call → summary + exactly 3 quick wins, 3 high-impact changes, 3 strategic recommendations, each citing supplied evidence.

8
scoreReport output

Validates everything against reportSchema and emits the final { narrative, report, evidence } structure consumed by the UI.

04 Suspend, resume & persistence

The trickiest part of the system: the workflow pauses for human confirmation, the stream is teed so a copy can be persisted to memory, and a resume request must prove the run is genuinely suspended before continuing.

① First turn — start & pause

  • /api/chat validates body, resolves visitor cookie → resourceId
  • Confirms thread ownership (getOwnedConversationThread)
  • Streams the agent; stream.tee() splits client vs persistence copy
  • persistSuspendedWorkflowPart drains the second copy and saves the suspended snapshot (with a stable runId) to memory

② Second turn — resume

  • UI posts { workflowResume: { runId, confirmed } }
  • handleWorkflowResume reloads stored messages and checks both the message snapshot and live run state are suspended
  • handleWorkflowStream resumes with the resume data
  • persistFinalWorkflowPart saves the final snapshot + a hidden hiddenWorkflowContext text message so later chat turns “know” the result

The suspension processor & auto-resume override

activeWorkflowSuspensionOnlyProcessor (input processor) strips suspendedTools/pendingToolApprovals metadata that belong to stale runs, keeping only the latest suspended run’s id. Meanwhile getAutoResumeOverride in the chat route walks recent messages and disables auto-resume when the newest workflow part is not a live suspended run — preventing the agent from auto-firing a dead confirmation. These two guards overlap conceptually and are the most fragile, hardest-to-follow code in the repo.

05 Services & data sources

Pure-ish modules under mastra/services. All network responses are validated and normalized; failures degrade gracefully into evidence notes rather than crashing the audit.

apple-client.ts

iTunes client

lookupApp, getRecentReviews, searchRelatedApps. Hand-written defensive parsers + typed error classes. Injectable fetch for testing.

listing-page-evidence.ts

Firecrawl scraper

Scrapes markdown + HTML + JSON. Extracts subtitle, promo text, in-app events, and filters mzstatic screenshot URLs by dimension/aspect ratio.

market-signal-evidence.ts

Market signals

Thin orchestrator: fires reviews + related-apps in parallel via allSettled, collecting notes for any branch that fails.

06 Findings — cleanup & improvements

Concrete issues spotted while reading the Mastra code, grouped by type. None block functionality; most reduce surface area, duplication, or fragility.

Dead code Duplication Naming / placement Robustness / smell
dead Unused appLookupTool + duplicated schema

The createTool(...) in tools/app-lookup-tool.ts:41 is never imported. The workflow uses the plain lookupAppMetadata() helper directly. Its hand-written outputSchema (lines 48–83) also duplicates appMetadataSchema in schemas.ts — two definitions that can silently drift.

Fix: delete the tool object (and the duplicate schema); keep only lookupAppMetadata + parseAppLookupInput. If a tool is wanted later, derive its schema from appMetadataSchema.
fixed Four near-identical generate* functions

Extracted runScoredGeneration(context, config) — a single helper that owns the shared generate({maxSteps:1, toolChoice:'none'}) call, the .object guard, abort-rethrow, and deterministic fallback. Each of the four functions is now a declarative config object only. ~100 lines of structural duplication removed from tools/report-tool.ts.

fixed Thread-title generation configured twice

Exported THREAD_TITLE_INSTRUCTIONS from conversation-agent.ts as the single source of truth. chat/route.ts now imports that constant instead of re-declaring an identical string literal.

name report-tool.ts contains no tool

It lives in tools/ and is named *-tool, but exports only agent-invocation / scoring helpers — no Mastra createTool. Same for lookupAppMetadata sitting beside the unused tool.

Fix: move scoring helpers to services/scoring-service.ts; reserve tools/ for actual registered tools.
name parseAppLookupInput exported but local-only

Only consumed inside its own module. Unnecessary public surface.

Fix: drop the export unless a test needs it.
smell extractInAppEvents returns at most one event

In listing-page-evidence.ts:371 the schema/return type is an array, but the code only ever emits [{ title: eventLines[0], description: eventLines[1] }].

Fix: either parse multiple event cards into the array, or narrow the type/docs to reflect “single representative event”.
smell Observability fixed to realtime

index.ts always uses strategy:'realtime' — great for Studio, heavier for production traffic.

Fix: gate strategy by NODE_ENV (realtime in dev, batched in prod).
smell Overlapping suspension guards

activeWorkflowSuspensionOnlyProcessor and getAutoResumeOverride both reason about “which suspended run is still live”. The logic is duplicated across an input processor and the route handler, and is the hardest code in the repo to follow.

Fix: centralize “latest live suspended run” detection in one shared helper that both paths call.
